## Earlier wallet interface

A presentable chat UI over the real `src/` analysis pipeline. Built for a
college demo, separate from the research pipeline's own honesty
constraints on the trained model's AUC (see `docs/RESEARCH_NOTES.md`) --
this app shows concretely-detected on-chain events (real swaps, real
rug-pull losses in SOL, real slippage) rather than the untrustworthy
model probability.

Does **not** execute any real transaction, and does **not** claim online
learning or a validated predictive model -- those are the specific claims
flagged as overreach vs. what's actually built.

## How it works

- `backend/main.py` — FastAPI app. Reuses `src.labels.build_labels` and
  `src.features.wallet_features` directly (no separate model). For any
  wallet already in `data/raw/`, analysis is instant; for a new address it
  fetches live from the public Solana RPC (can be slow — public RPC is
  rate-limited).
- `frontend/index.html` — single-file chat UI, no build step.
- Two curated demo wallets (one with real rug-pull losses, one clean) are
  hardcoded in `main.py` for demo reliability, since live RPC lookups can
  be slow mid-presentation.

## Integrated live prototype

Open **http://127.0.0.1:8430/live**. The single flow accepts a proposed plain SOL
transfer, performs current network checks, builds fresh historical features,
runs the actual trained HGB models, and saves the observation before any receipt
is attached. The download contains the exact unsigned candidate and message hash.
Receipt verification refuses a different message, an older outcome or a duplicate
link. No signing or transaction submission exists in this application.

From the repository root, use the existing ML requirements and export, then
collect recent histories and start the server:

```sh
.venv/bin/python -m pip install -r research/solana/ml/transaction_requirements.txt
OMP_NUM_THREADS=4 OPENBLAS_NUM_THREADS=4 .venv/bin/python research/solana/ml/export_demo_models.py
OMP_NUM_THREADS=4 OPENBLAS_NUM_THREADS=4 .venv/bin/python research/solana/fee_proof/collect_live_history.py --network devnet --blocks 16
OMP_NUM_THREADS=4 OPENBLAS_NUM_THREADS=4 .venv/bin/python research/solana/fee_proof/collect_live_history.py --network mainnet --blocks 8
OMP_NUM_THREADS=4 OPENBLAS_NUM_THREADS=4 .venv/bin/python -m uvicorn webapp.backend.replay:app --host 127.0.0.1 --port 8430
```

Model export requires the existing processed training/validation/test files;
their reproduction is documented in `research/solana/ml/README.md`. This is a
local prototype. Refresh the desired history within one hour of presentation.
The page's **Refresh historical inputs** button can collect it without a terminal.
The collector uses public RPC and can take roughly a minute per network; outages
and partial coverage are explicit. The initial verified samples contain 302
devnet and 8,871 mainnet transactions over roughly eight hours each. Current RPC
readers request transaction version 1 support and use parsed declared roles;
the proposed transfer and receipt linker support a single legacy SOL transfer.

Scores are withheld for stale snapshots, wrong networks or fewer than 100 mature
records spanning six hours. The exact research `ParticipationHistory` extractor
enforces a one-hour outcome delay. Fresh sampling differs from the archive, so
displayed model outputs are experimental scores, with no validated live
probability, calibrated warning or ML-driven blocking. The current network
result is shown separately. Input-range checks are diagnostics, not a guarantee
of generalisation. This adds working inference, not proof of predictive validity.

Study observations are stored locally at
`data/processed/solana_ml/prospective.sqlite3`. `/api/study` lists observations;
`/api/study/{decision_id}` returns a recorded decision. The check is unsigned
(`sigVerify=false`), so it must not be called signed submission preflight.
Receipts are fetched read-only and must match the exact checked message, occur
in a later slot and not predate the recorded decision. A rebuilt blockhash changes
the message and requires a new check. No receipt means an unknown outcome.
Actual receipt fees and elapsed observation duration are not fee or time savings.

For a separately signed plain legacy transfer, `/api/live/signed-observe` accepts
its base64 transaction, keeps its blockhash unchanged and runs simulation with
`sigVerify=true`. It records the resulting model observation without submitting
the transaction. Use `research/solana/fee_proof/observe_signed.py --network devnet
--transaction-file signed_transfer_base64.txt` while the server is running.
The file must contain an already signed transaction, never a private key or
keypair. This is a signed simulation observation, not a recorded
`sendTransaction` preflight event. The local verification also checks a real
signature-verified simulation before submission on its isolated validator.

The separate local fee experiment also executes a real signed successful test
transaction through this decision/receipt store. Its verification is in
`docs/results/solana_prospective_local_verification.json`. No real funds are used.
For causal ML savings, an authorised prospective comparison against signed
preflight alone and a defensible cost model are still required.

Presentation sequence: choose **Small transfer**, run the combined check, explain
the network result and experimental ML outputs, inspect the recorded decision,
then open **Evidence** to show the measured local fees and the full historical
audit including false alarms. Show an insufficient-balance example next. Public
example outcomes can change; explain the actual returned result.

## Reproducible local fee experiment

Open http://127.0.0.1:8430/fee-proof for the measured comparison and raw receipts.
To repeat it, install the Solana CLI and run:

```sh
.venv/bin/python -m pip install -r research/solana/fee_proof/requirements.txt
.venv/bin/python research/solana/fee_proof/run.py
```

The script starts an isolated loopback validator, uses throwaway wallets and
local airdrops, verifies all balance changes against confirmed receipts, then
stops only its own validator. It never changes the default wallet or CLI config.
Ports 8897, 8898 and 9917 must be free. Its isolated ledger and logs are retained
under ignored `data/raw/fee_proof/`; public evidence is saved to
`docs/results/solana_local_fee_proof.json`. Refresh the page after rerunning.

The verified run measured 5,000 lamports (0.000005 test SOL) charged for an
execution failure; the recipient received nothing. The matching check-and-stop
attempt cost zero. A valid transfer separately demonstrated principal plus fee.
The paid failure deliberately bypassed preflight **only in this local script**.
Normal preflight rejected the same error at zero cost too. This proves the
fee mechanism and avoidance versus a forced failing submission, not improvement
over ordinary preflight, mainnet savings, ML-driven savings or time saved.
The production checker remains read-only, with no submission endpoint.

### ML fee-policy audit: current claim is not proven

The follow-up evaluates the exact deployed calibration/thresholds and fixed
cost-based thresholds on all five historical test periods: **102,443 cold-history
transactions**, including 6,410 failures. No threshold was selected to maximise
these test outcomes. This is an exploratory diagnostic on already-inspected
dates, not a fresh confirmation.

On December 5, the deployed context-model threshold warns on 357 failures and
649 successful transactions. At the fixed 83.3% threshold, it warns on 15 failures
and one success, but another period yields 53 failures and 53 successes. Pooled
across periods, that stricter rule warns on 107 failures and 60 successes and
misses 6,303 failures. All three positive cost-ratio scenarios have negative
pooled hypothetical utility for the context model. These are assumed costs in
dimensionless fee units, not measured financial losses or savings.

The source schema lacks preflight outcomes and actual fees. Therefore the
incremental fee-saving claim is unidentifiable from this sample: even every
correct ML warning might already be caught by standard preflight. Better AP does
not establish a useful blocking policy. Keep the current model as a research
warning comparison rather than an automatic transfer gate.

Reproduce each cohort (`pilot`, `confirmation`, `extension`, `prospective`, `fresh`),
then build the combined audit:

```sh
OMP_NUM_THREADS=4 OPENBLAS_NUM_THREADS=4 .venv/bin/python research/solana/fee_proof/evaluate_ml_policy.py --cohort fresh
.venv/bin/python research/solana/fee_proof/summarize_ml_policy.py
```

The combined report, all results, source/model hashes and the required prospective
study design are in `docs/results/solana_ml_fee_policy_summary.json`, displayed
under `/fee-proof`. The next study must record preflight and ML before outcomes,
then receipts/fees for submitted candidates, with the main analysis restricted to
candidates that passed standard preflight. Shadow-mode prediction is the first
step; proving causal savings requires an authorised policy comparison afterward.

1. State the question: can shared account history help when a signer has no

2. Show a case's signer and declared accounts. Explain that writable accounts may

   examples were selected using outcomes for illustration; the chronological
   examples and full test metrics prevent confusing anecdotes with evaluation.
6. Show the full-cohort table, including the period with no follow-up alerts.
   Lower false alarms alone do not establish a better detector if recall falls.
7. Explain the separate paper endpoint: identity-controlled AP rose from 0.1688

## Presentation questions

- **Is this AI/ML?** Yes. Gradient-boosted models learn from past outcomes; explicit
  account participation features represent historical context. There is no new
  learning architecture claim.
- **What is new?** The specific cold-history/first-appearance benchmark and the
  tested contribution of writable-account history after strong controls. The
  reviewed prior work does not establish worldwide originality.
- **Is it ready for deployment?** No. False-positive control drifts, simulation
  has not been compared live, and unlanded transactions are absent.
- **Is a failure always bad?** No. Protective checks can intentionally reject an
  operation. The target is observed execution failure, not fraud or financial harm.
- **How is leakage avoided?** Chronological splits, purged label availability,
  delayed online history, excluded current execution metadata and validation-only
  fitting of calibration/thresholds. Test-time history still legitimately uses
  earlier matured test outcomes, as stated in the protocol.

## Additional unused-date result

A fifth window uses December 3-5, 2025, with model/history/identity settings and
the calibration recipe fixed before those transaction outcomes were loaded.
Alternate shards are selected by a fixed date/seed hash using file counts.
The December 5 test includes 21,581 cold-history rows and 19,515 first appearances.
The identity-controlled first-appearance AP is 0.2207 versus 0.2393: gain +0.0186,
paired-hour 95% interval [+0.0095, +0.0288]. This supports the narrower ranking
finding on another date, still from the same provider and sampling scheme.

For the original history-only context model, the calibration follow-up changes
cold-history recall from 6.61% to 29.87%, while FPR rises from 0.32% to 3.18%.
Brier loss improves slightly from 0.04647 to 0.04620; AP falls from 0.2640 to
0.2388 because isotonic mapping introduces ties. These are operating tradeoffs,
not a claim of universal improvement. Earlier-period failures remain visible.
